## 0. The finding that shapes everything else

**This repository is empty.** At Phase 0 it had no commits, no source, no tests,
no package manifest — nothing. `.qa/adapters/detect.sh` reports `custom`.

The build spec assumes a *target repository* with a stack to test (§15 Q1–Q16 all
presuppose one). That assumption does not hold here, and no other repository is
in this session's scope. So this repo has been built as **the QA team kit
itself**: a stack-agnostic, installable system whose stack-specific behaviour is
supplied by an adapter (`.qa/adapters/`) once it is dropped into a real codebase.

Consequences, stated plainly rather than papered over:

- Everything **stack-independent** is built and, where testable, proven:
  the capability probe, the gates, the guard hooks, the agent roster, the
  skills, the commands, the CI workflows.
- Everything **stack-dependent** is a `<<PLACEHOLDER>>` resolved by the adapter,
  and is marked as such below. §15 Q1–Q16 cannot be answered without a codebase.
- **§15 Q17 and Q20 remain open and need a human.** They are the two questions
  no amount of code reading can answer. See §6 below.
- Phase 2's acceptance bar ("≥15pp mutation lift on three real files", "≥60%
  human acceptance") is **not claimable here** — there are no real files and no
  human reviewer. It carries over to first installation.

## 2. Permission semantics — measured, because the intuitive reading is wrong

Established with a **positive control** (Bash allowlisted → it really did run),
so the negative results below mean "denied", not "the model chose not to".
All measured by filesystem side effect, never by reading the transcript.

| Invocation (`claude -p`) | Bash executed? |
|---|---|
| `--allowedTools "Bash"` | **yes** |
| `--allowedTools "Read"` | no |
| `--permission-mode dontAsk`, no allowlist | no |
| `--permission-mode dontAsk --allowedTools "Read"` | no |
| `--tools "Read"` | no |
| `--disallowedTools "Bash"` | no |

Reading:

- `--allowedTools` is a **permission allowlist**. In non-interactive `-p` mode an
  un-allowlisted tool has nobody to approve it, so it is denied in practice.
  Interactively it only *pre-approves* and restricts nothing — do not rely on it
  as a restriction outside CI.
- `--permission-mode dontAsk` does **not** widen the allowlist. It suppresses
  prompts; it does not grant.
- `--tools` and `--disallowedTools` restrict unconditionally, in either mode.

**Design consequence:** P4 separation of duties uses defence in depth —
`--tools` to shape the surface, `--disallowedTools` to deny, `--allowedTools` to
scope permissions, and the G5 hook as the backstop that actually adjudicates
paths. The hook is not redundant: see §3.

### Two escalation routes worth knowing about

Observed during probing, unprompted:

1. Denied Bash, the model offered to **"spawn an agent that has Bash access"** —
   i.e. to route around its own restriction by delegating. This is exactly why
   G5 is enforced by a hook keyed on `agent_type` rather than by tool lists
   alone: a subagent's calls are intercepted by the same guard.
2. Blocked by a path guard, the model asked the user to **"relax these
   permissions"**. §7.1 predicts this. It is why an agent that must produce a
   file is given a `Write` scope that actually covers its deliverable — an agent
   that cannot do its job will lobby to have the constraint removed.

## 6. The two questions that required a human — both now answered

**Q17 — ANSWERED (2026-08-08): fast rollback, no flags, no staged rollout.**

`SHIP_WITH_WATCH` is enabled, because a change *can* be undone in minutes. But
rollback is coarser than a flag, and the design reflects that rather than
glossing it:

- A rollback reverts **the entire deploy**, including unrelated work.
- Minutes is not instant; damage accrues inside the window.
- Some changes are not reversible by redeploying old code at all. G7 rejects
  `SHIP_WITH_WATCH` when the diff touches `rollback_unsafe_paths` — migrations,
  billing, payments, backfills. Rolling back a migration is frequently worse
  than the bug that prompted it.

**Follow-up worth measuring:** `rollback.typical_minutes` is currently a guess
(5). It sets how long a "watch" window has to be useful, so replace it with a
real number from an actual rollback.

**Q20 — ANSWERED (2026-08-08, repository owner).**

> "No bugs, no inaccuracies, no faulty logic, no faulty math, no contradictions."

Decomposed into five measurable criteria in `.qa/RISK-RULES.yaml`
(`confidence_criteria`), and `release-marshal` now reports a status and basis for
each. The answer is purely about **correctness**, so the marshal leads with
correctness evidence and does not foreground latency, UX, scale or cost.

Recorded limitation: no test system can certify the *absence* of these five.
The marshal produces the strongest available evidence against each and names
where that evidence is missing. §17 already says this; the Q20 answer makes it
load-bearing, so the marshal is instructed to state it explicitly rather than
imply certainty.

Both recon questions that required a human are now answered. What remains open
is stack profiling (§4), which needs a target repository rather than a decision.
